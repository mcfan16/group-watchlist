How This Works, In Plain Language

The website is what you see and tap on your phone — the queue, star ratings, add-show screen.

A small helper function runs behind the scenes only when needed — fetching a pasted Rotten Tomatoes page and reading its details, since a phone's browser can't safely reach another website directly.

A shared database is a spreadsheet in the cloud that all three phones read from and write to, so everyone sees the same queue and each other's ratings.

Where It Runs & How to Try It

💻

Local development: npm run dev, then open http://localhost:3000 — this is what to record if the deployed version isn't ready.

🌐

Real family use: deployed on Vercel, connected to GitHub — each person opens the same URL from their own phone (optionally "Add to Home Screen" for an app-like icon).

🎬

Recommended demo: record the deployed version, ideally on multiple real phones — shows the actual kernel (separate people, separate devices, agreement forming live) far more convincingly than one browser tab. Test it thoroughly a day or two ahead; keep localhost as a fallback.

The Core Journey Through the System

1

Open on your phone → checks localStorage for a saved name → picks name once if none saved.

2

Fetches shows + ratings from Supabase → shows the Family view, sorted.

3

Empty queue → welcome message + "add your first show" prompt.

4

Tap "add new" → paste RT link → sent to app/api/parse-link → fetches & reads the page → editable preview → save → new row in shows.

5

New show appears at the bottom, unrated.

6

Anyone taps in, adds 1–5 stars → row written to ratings.

7

Views quietly re-check Supabase every 10 seconds (polling) and re-sort if anything changed — no manual refresh needed.

8

Swipe → Delete (row removed) or Mark Watched (status flips, moves to archive).

9

Switch to Personal view — same data, filtered/sorted for solo picks.

Look and Feel

Warm and clean/minimalist. A warm terracotta orange as the primary accent, paired with a soft teal and a muted rose as complements. System font stack — no custom web font to load. Generous white space, rounded cards, calm rather than busy. Plain CSS expresses this fully.

Interface copy catch: the star control isn't a post-watch "rating" — it's a pre-watch gauge of interest. Label it that way: "How interested are you in watching this?" rather than "Rate this show." The rest of the interface text should follow that same warm, casual, family-note voice — not generic form labels — written consistently as each screen gets built.

Important Failure Modes

  • RT link can't be fetched/parsed → error message, retry the link, or jump to manual entry.
  • RT link parses only partially → editable preview leaves that field blank; saving isn't blocked.
  • Empty queue → welcome message + add-first-show prompt, never a blank/broken screen.

What Was Simplified and Why

  • 10-second polling, not true real-time sync — quietly re-checks Supabase every 10 seconds rather than an instant push connection. Nearly the same felt experience, without websockets or Supabase's realtime feature, which are harder to build and debug.
  • Status flag, not a separate archive table — "watched" just flips a field. Same result, simpler to build.
  • No accounts — a one-time per-device name pick covers identity for 3 known people.
  • Plain CSS, no UI framework — one fewer thing to learn; the warm/minimal look doesn't need a design system.
  • No app-store distribution — "Add to Home Screen" gives an app-like icon without a paid developer account or review process.
Decisions & Open Issues
  • Deployed on Vercel, not local-only — the family wants to actually use this on their own phones after the hackathon, not just demo it once.
  • Family score computed live from the ratings table — always current, never a stale precomputed value.
  • Investigated uncertainty: whether Rotten Tomatoes exposes enough data to a plain fetch (no official API exists). Tested against two real pages — all target fields were present in the fetched content. Strong signal the plan works; the parsing code itself still needs writing and testing against more pages early in the build.
  • Carried from the PRD's open question: the exact field list may need small adjustments once tested more broadly (many-season shows, older or sparse titles) — expected to affect which fields auto-fill vs. need manual entry, not the architecture itself.
